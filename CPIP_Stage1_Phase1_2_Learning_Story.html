Stage 1 — Phase 1.2
Core Placement Data Model

What I Built

In Phase 1.2, I designed the database schema and data model that powers CPIP's agent coordination and decision-making.

The 6 Tables

  • ✅ STUDENT — 14 fields storing student profiles, skills, and career goals
  • ✅ SKILL — 5 fields for available skills in the system
  • ✅ STUDENT_SKILL — links students to their skills with proficiency levels
  • ✅ JOB — 10 fields storing job opportunities from employers
  • ✅ JOB_REQUIREMENT — links jobs to required skills (mandatory/optional)
  • ✅ ASSESSMENT — 7 fields storing readiness evaluation scores

Deliverables Created

  • ✅ Database schema design document
  • ✅ Entity-Relationship Diagram (ERD)
  • ✅ Sample seed data (3 students, 5 skills, 3 jobs)
  • ✅ Schema explanation and relationships

Career & Placement Domain Learning

I learned that placement readiness depends on organizing information in a structured, queryable way.

Key Insight:

A placement platform needs to organize student information (profile, skills, projects, career goals) so that CPIP can match students with job requirements and recommend suitable roles accurately. Without a data model, this becomes impossible.

Why Data Model Matters

In placement, we need to answer questions like:

  • 🔍 "Which students have Python skills?"
  • 🔍 "Which jobs require SQL?"
  • 🔍 "Is this student eligible for this job?"
  • 🔍 "What is the skill gap for this student?"

A proper data model makes these queries efficient and accurate.

Agentic AI Learning

I learned that agents cannot work together without a common data structure.

The Problem Without Data Structure:

If Skill Gap Agent stores data one way, Resume Agent another way, and Portfolio Agent a third way, they cannot coordinate. The system breaks down.

The Solution With Data Model:

A unified data schema ensures all agents use the same "language" for data. Skill Gap Agent output feeds into Role Matching Agent. All agents read from and write to the same structured tables.

Agent Coordination Flow

┌─────────────────────────┐ │ STUDENT TABLE │ │ (Profile, Skills, etc) │ └──────────┬──────────────┘ │ ├─→ Skill Gap Agent reads STUDENT_SKILL │ → compares with JOB_REQUIREMENT │ → writes to ASSESSMENT table │ ├─→ Portfolio Agent reads STUDENT table │ → evaluates projects │ → writes to ASSESSMENT table │ └─→ Role Matching Agent → reads all ASSESSMENT scores → compares with JOB table → recommends suitable roles

Database Schema Overview

STUDENT Table (14 fields)

Field Type Purpose
id (PK) Integer Unique student ID
name String Student's full name
email String Contact email
degree String Academic degree (BBA, B.Tech, etc)
cgpa Float Academic performance score
target_role String Career goal (AI Engineer, Backend Dev)
github_link String Portfolio link
salary_expected Integer Expected salary range

Key Relationships

One-to-Many:

One STUDENT has Many STUDENT_SKILLs (student knows multiple skills)

One SKILL is known by Many STUDENT_SKILLs (skill is learned by multiple students)

One JOB has Many JOB_REQUIREMENTs (job requires multiple skills)

Many-to-Many:

Students ↔ Skills (via STUDENT_SKILL table)

Jobs ↔ Skills (via JOB_REQUIREMENT table)

Key Takeaway

Data structure enables agent coordination.

In Phase 1.1, I learned agents need infrastructure (backend, database, frontend). In Phase 1.2, I learned agents need organized data. Without a data model, agents cannot work together because they won't understand each other's data formats. With a proper schema, all agents use the same "language" and can coordinate seamlessly.
